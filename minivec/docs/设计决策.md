# 设计决策:每个功能"为什么这么选"

真实开发里,每做一个功能都站在岔路口:有几种实现方式,各有利弊,最后选一条。
这份文档把 MiniVec 里的关键岔路口都记下来——**需求 → 几种方案 → 权衡 → 选择与原因**。
面试讲项目时,这种"我为什么这么选"比"我实现了什么"值钱得多。

---

## 决策 1:存储和检索,合一还是分离?

**需求**:既要存向量,又要按相似度检索。

| 方案 | 做法 | 优 | 缺 |
|---|---|---|---|
| A 合一 | 像 kvstore 的 array 引擎,存储自带查找 | 简单,一个模块 | 检索逻辑塞进存储,换检索策略要动存储 |
| B 分离 | `vector_store`(只存) + `index`(只搜) | 同一份数据可挂暴力/HNSW;职责清晰 | 多一层抽象 |

**选 B。原因**:相似度检索策略多(暴力/HNSW/IVF/量化)且复杂,不像精确匹配能顺手塞进存储。分离后,存储稳定、索引可替换,这是整个项目可扩展的根。

## 决策 2:ANN 索引用哪种?(项目最核心的选型)

**需求**:百万级向量里快速找最相似的 K 个,暴力 O(N) 太慢。

| 方案 | 代表 | 优 | 缺 |
|---|---|---|---|
| 暴力 | flat | 100% 准 | O(N·D),慢 |
| 树 | KD-tree/Ball-tree | 低维快 | **高维失效**(维度灾难) |
| 哈希 | LSH | 实现简单 | 召回一般,要调很多桶 |
| 量化 | IVF/PQ | **省内存** | 有精度损失,训练码本麻烦 |
| 图 | **HNSW**/NSG | **高召回 + 高速 + 增量插入** | 内存大,删除难 |

**选 HNSW。原因**:① 召回和速度综合最好(recall 0.99 时仍 O(log N));② 支持增量插入(VADD 实时建图),不像 IVF 要先训练;③ 和我刚写过的跳表同源(分层加速),迁移成本低。
**代价我接受**:内存换速度;删除难 → 用墓碑(见决策 4)。
**保留暴力**:不是没用,而是当 HNSW 的"标准答案"算召回率。

## 决策 3:topK 怎么选?全排序 vs 堆 vs nth_element

**需求**:从 N 个打分结果里取最大的 K 个。

| 方案 | 复杂度 | 备注 |
|---|---|---|
| 全排序后取前K | O(N log N) | 简单但浪费(只要 K 个却排了全部) |
| **大小为K的堆** | **O(N log K)** | 边扫边维护,空间 O(K) |
| nth_element/快选 | O(N) 平均 | 最快但需要拿到全部数据、会打乱 |

**选堆。原因**:K 远小于 N 时 O(N log K) 明显优;且**流式**——数据一边产生(遍历库/图扩展)一边喂堆,不用先攒全部。HNSW 的 search_layer 也复用这套堆思想。

---

## 决策 4:度量方向不统一,怎么处理?

**需求**:COSINE/DOT 越大越相似,L2 越小越相似,方向相反,堆逻辑会分叉。

| 方案 | 做法 | 缺 |
|---|---|---|
| A 两套堆 | COSINE 用小顶堆,L2 用大顶堆 | 堆代码写两遍,主循环到处 if metric |
| B 方向统一 | 把所有 metric 算成"score 越大越相似"(L2 取负) | 几乎无缺点 |

**选 B。原因**:把"分类判断"收敛到一个 `score_by_metric` 函数(一个 switch),堆永远是同一套小顶堆。少写一套易错代码,这是"用数据变换消除控制分支"的典型手法。

---

## 决策 5:删除怎么做?物理删 vs 墓碑 vs 墓碑+重建

**需求**:VDEL 删一条,但它可能还在 HNSW 图里被引用。

| 方案 | 做法 | 优 | 缺 |
|---|---|---|---|
| A 物理删 | 数组搬移 + 改图 | 干净 | 要搬数组、改图连通性,极复杂易错 |
| B 墓碑标记 | 标记失效,遍历时跳过 | O(1),简单 | 空间不回收,图里仍是死点 |
| C 墓碑 + 定期重建 | B + 攒够了整体重建 | 兼顾 | 多一套重建逻辑 |

**选 B(起步),预留 C。原因**:物理删 HNSW 图是出了名的难(删点破坏连通性)。墓碑 O(1) 先把功能跑通;真到内存吃紧,再加"定期重建"。**先正确再优化**,不为一个边缘需求引入大复杂度。

## 决策 6:持久化——存什么?

**需求**:重启不丢数据。

| 方案 | 存什么 | 优 | 缺 |
|---|---|---|---|
| A 只存裸向量 | id + vec | 格式简单、健壮、跨版本稳 | 加载要**重建 HNSW**,O(N log N) |
| B 存向量+图 | 再 dump 邻居表/层级 | 加载快(直接恢复) | 图结构序列化复杂、和实现强绑定、易损坏 |
| C mmap 整个结构 | 内存直接映射文件 | 启动极快 | 指针/对齐/可移植性地狱 |

**选 A。原因**:学习项目优先"健壮 + 简单"。只存向量,格式就是 `头 + (id,vec,meta)*N`,谁都能解析、改了 HNSW 实现也不影响存档。**代价(加载重建图)可接受**——加载是低频操作,且重建顺便验证了图正确性。N 真的很大再考虑 B。

---

## 决策 7:持久化——何时触发?写盘怎么保证不损坏?

**需求**:server 是 epoll 死循环,没有自然的"退出存盘"时机。

**何时存**:

| 方案 | 缺 |
|---|---|
| 进程退出钩子 | 被 `kill -9` 就丢;epoll 循环也没干净退出点 |
| **SAVE 命令(显式)** | 要客户端主动触发,但可控、简单 |
| 定期快照 | 要定时器/线程,且快照间隙仍会丢 |
| WAL(写前日志) | 最稳,但要给每条写操作记日志,重 |

→ **选"SAVE 命令"**:起步够用、不引入定时器/线程。日后要"不丢"再上 WAL。

**写盘安全**:

| 方案 | 缺 |
|---|---|
| 直接覆盖原文件 | 写一半崩 → 旧档也毁了 |
| **写 tmp + rename** | rename 在 POSIX 是原子的,崩了顶多丢新档,旧档完好 |

→ **选 tmp + rename**:一行成本,换来"崩溃不毁旧档"。这是工程通用套路。

## 决策 8:网络分帧——固定长度 vs 分隔符 vs 长度字段

**需求**:TCP 是字节流,一条 ~3.5KB 的 VADD 会被拆成多个包,要正确切出"一条命令"。
(这个坑是 live 测试当场踩出来的:原来"一次 recv=一条命令"在大命令上直接崩。)

| 方案 | 做法 | 优 | 缺 |
|---|---|---|---|
| 固定长度 | 每条定长 | 解析最简单 | 向量维度变就废,浪费 |
| **分隔符 `\n`** | 按换行切 | 文本协议天然,调试用 nc 友好 | 内容含分隔符要转义(我们没这问题) |
| 长度字段 | 包头写 body 长度 | 通用、适合二进制 | 要维护状态机读包头+包体 |

**选分隔符 `\n`。原因**:我们是文本协议,命令天然一行一条;`\n` 切分实现简单、`nc`/Python 直接能用。攒不满一行就留着等下次 recv(半包处理)。要上二进制协议时再换长度字段。

## 决策 9:协议——文本 vs 二进制 vs RESP

**需求**:客户端和 server 怎么编解码。

| 方案 | 优 | 缺 |
|---|---|---|
| **文本(空格分隔)** | `nc` 直接调、肉眼可读、好调试 | float 传文本慢且丢精度、体积大 |
| 二进制 | 快、精度无损、体积小 | 要写编解码、不能肉眼看 |
| RESP(Redis 协议) | 成熟、生态广 | 对这个项目过重 |

**选文本(起步)。原因**:学习/调试阶段"可读 + 能 nc 手敲"价值最大。性能瓶颈真出现(传 384 个浮点),再切二进制——而且架构上只动协议层,不影响引擎。

---

## 决策 10:embedding 放哪?server 内置 vs 客户端

**需求**:文本要变向量,这步放哪。

| 方案 | 做法 | 缺 |
|---|---|---|
| A server 内置 | C server 里跑模型 | C 调 Python/模型很别扭,server 被绑死在某模型/某语言 |
| B 客户端做 | `embed.py` 转好向量再发 VADD | server 保持纯粹(只管向量),但客户端要维护 id→原文 |

**选 B。原因**:**职责分离 + 解耦**。向量数据库就该只懂向量,不该绑定 embedding 模型(换模型、换语言都不该动 server)。Milvus/Qdrant 也是这个边界:库存向量,embedding 在外面做。

---

## 一句话总纲

> 这些选择有个共同的口味:**先正确、先简单、先解耦,把"快/省/全"留到真有瓶颈时再换**——而且每次都让"要换的东西"被一层抽象挡住(换索引不动存储、换协议不动引擎、换模型不动 server)。这就是架构的意义。
